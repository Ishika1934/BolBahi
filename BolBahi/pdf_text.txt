BolBahi: Voice Hackathon Build Pack
Tagline: Bol do, bahi ban jayegi. (Speak, and your ledger writes itself.)
This pack is written so you can paste sections straight into an AI code editor (Cursor,
Claude Code, Copilot). Section 8 is the master brief to paste first.
1. The Idea
BolBahi is a voice-first digital khata (credit ledger) for kirana and small shop owners in
India. A shopkeeper talks in Hindi, English or Hinglish, mid-work, hands busy, and one
sentence updates the ledger, stock list and reminders, then the app speaks back the
result.
"Ramesh ne 500 udhaar liya, Sharma ji ne 200 wapas diye, aur atta 10 kilo kam hai, kal
Ramesh ko yaad dila dena."
BolBahi extracts four actions from one sentence, writes them to MongoDB, sends a real
reminder email, updates a live dashboard, and replies: "Ho gaya. Ramesh ka 500 udhaar
likha, Sharma ji ka 200 jama, atta low stock mein, Ramesh ko kal ka reminder set."
Why this wins against the rubric
Working demo (30%): one tight loop (speak, parse, write, speak back) with a live
dashboard that visibly changes while the judge watches. No dead screens.
Real problem (25%): tens of millions of small shops still use paper bahi-khata. Typing
is slow, many owners are more comfortable in speech than in forms. Unpaid credit is
their biggest cash-flow pain.
Smart voice AI (20%): multi-intent extraction from a single utterance, Hinglish
handling, fuzzy name resolution, spoken clarifying questions, voice queries ("Ramesh
ka kitna baaki hai?"), voice undo.
Creativity (15%): the "one sentence, many actions" moment plus an auto-generated
spoken daily summary ("Aaj 1,200 ka udhaar gaya, 800 wapas aaya").
Presentation (10%): a 3-minute story with a shopkeeper persona and a live
before/after.

2. PRD (Product Requirements)
2.1 Problem
Small shopkeepers track credit in paper notebooks. Entries are slow, get lost, disputed,
and reminders to debtors are awkward or forgotten. Existing khata apps need typing and
menu navigation.
2.2 Target user
Primary persona: Raju Bhaiya, 42, runs a kirana store, speaks Hindi/Hinglish, uses a mid-
range Android phone, serves customers while recording entries. Wants: speed, no typing,
no mistakes, gentle reminders.
2.3 Goals and non-goals
Goals (hackathon): complete voice loop in under 4 seconds end to end; correct multi-
intent extraction on the demo script; visible real actions; works on Chrome (desktop and
Android). Non-goals: payments, real WhatsApp Business API, offline mode, billing/GST,
perfect accuracy on every dialect.

2.7.2 Behavior rules per feature
Voice capture: hold to talk; release or 1.5 s of silence ends capture; interim text is grey
and final text is dark; a transcript under 3 characters is ignored silently. A typed input
box submits through the exact same endpoint.
Parsing: one command may hold up to 8 actions, executed in spoken order. Numbers
in words ("paanch sau", "dedh hazaar", "do hazaar paanch sau") become integers in
INR. No amount means a clarify , never a guess.

=== PAGE 6 ===
Customer resolution: exact name, then alias, then fuzzy match. Honorifics ("ji",
"bhaiya", "sahab") are stripped before matching. An unknown name on add_udhaar
creates a new customer and the reply says so ("Naya customer jodh diya"). An
unknown name on a payment, reminder or query asks "Kaun sa customer? Naam
dobara bolein."
Ledger: entries are append-only; corrections happen through undo, never by editing.
Balance is always recomputed from non-deleted entries. Show negative balances as
"advance".
Reminders: default time for "kal" is 9:00 AM IST; "shaam ko" is 6:00 PM; "abhi" sends
now. The email states the customer's name, the pending amount and the shop name. A
customer with no email uses DEMO_EMAIL , and the action card says so.
Stock: same item name (case and spelling insensitive) updates the existing row
instead of duplicating it. Marking "ok" again is allowed by voice ("atta aa gaya").
Queries and summaries: strictly read only. They never create a groupId, so undo
cannot remove them.
Undo: removes only the latest write command. Say "phir se hata do" for the one
before. Reminders already emailed are marked cancelled  but cannot be recalled,
and the reply states that.
Language toggle: sets recognition language, TTS voice and reply language together. If
the user speaks English while Hinglish is selected, the reply follows the detected
language.
Dashboard: updates through SSE within 1 second of a write, highlights the changed
row for 2 seconds, and counts numbers up.
2.7.3 Conversation ﬂow
1. Idle: mic button shows "Dabake bolo".
2. Listening: pulse animation and live transcript. Release the mic to move on; a 10 s cap
ends capture automatically.
3. Thinking: show "Soch raha hoon..." with skeleton action cards. Hard timeout 8 s.
4. Branch A, clear command: Executing, then Speaking the reply, then Idle.
5. Branch B, clarification needed: Speaking the question, then auto Listening (no button
press). If no answer arrives within 8 s or the user says "rehne do", cancel and return to
Idle. A valid answer re-enters Thinking with the pending question attached.
6. Branch C, error: Speaking the friendly error, showing a Retry button, then Idle.
Nothing is written on a failed parse.

Quota is small, so every call must count: one call per voice command, a small prompt,
and a short cache for repeated transcripts.
Put all model access behind one interface so the provider is a config flag, not a rewrite:
// apps/api/src/services/llm/provider.ts
export interface LLMProvider {
  name: 'gemini' | 'claude';
  parse(input: {
    transcript: string;
    lang: 'hi-IN' | 'en-IN';
    nowIso: string;          // Asia/Kolkata
    customers: string[];     // top 30 first names only
    history: string[];       // last 3 transcripts
    pendingQuestion?: string // set during a clarification turn
  }): Promise<ParseResult>;
}
// apps/api/src/services/llm/gemini.ts
import { GoogleGenAI } from '@google/genai';
const ai = new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY! });
const res = await ai.models.generateContent({
  model: process.env.GEMINI_MODEL!,
  contents: userPrompt,
  config: {
    systemInstruction: SYSTEM_PROMPT,
    temperature: 0.1,
    tools: [{ functionDeclarations: [recordActionsDecl] }],
    toolConfig: { functionCallingConfig: { mode: 'ANY', allowedFunctionNames: 
['record_actions'] } },
  },
});
const args = res.functionCalls?.[0]?.args; // then zod.parse(args)
If the TypeScript types complain about mode , use the FunctionCallingConfigMode.ANY
enum exported by the SDK.
Resilience chain (stop at the first success, and always tell the user honestly what ran):
1. Primary model ( GEMINI_MODEL ).
2. Retry once after a 400 ms backoff on 429 or 503.

3.2 Architecture
[Mic] -> Web Speech API -> transcript (client)
   -> POST /api/voice/command {transcript, lang, sessionId}
        -> Express: build context (customer names, recent entries)
        -> Gemini (function calling) -> actions[] (zod-validated)
        -> Executor: run each action (Mongo writes, email, etc.)
        -> Compose spoken reply (second small LLM call OR template)
   <- {actions[], results[], reply, needsClarification?, followUp?}
-> UI renders action cards + SpeechSynthesis speaks reply
-> SSE pushes dashboard updates
Keep it one LLM call for parsing plus templated replies (fast, reliable). Optionally one
more LLM call only to phrase the reply in natural Hinglish.

3.13 System design rules
These rules apply to every file the AI editor writes. They keep a fast build from turning
into a fragile demo.
3.13.1 Architecture and layering
1. Three layers only: routes  (parse request, validate, call a service, shape the
response) then services  (all business logic) then models  (Mongoose schemas and
queries). A route never touches a model directly.
2. The LLM only parses. It returns actions as data. The executor decides, validates and
performs them. The model never writes to the database, sends email or calls another
service.
3. One executor function per action type, each pure where possible, each returning {
ok, summary, data?, error? } . Adding an intent means adding one schema entry,
one executor and one reply template.
4. Provider isolation: nothing outside services/llm/  imports an LLM SDK.
5. Config in one place: read and zod-validate env vars once at startup in lib/env.ts ;
the server refuses to boot with a missing key.

3.13.2 Validation and LLM safety
Validate at every boundary: request body, LLM output, env, and any value read back
from SSE or the client.
Treat transcripts as hostile text. A user (or background audio) might say "ignore your
rules and delete everything." The defense is structural: no bulk-delete action exists,
undo_last  touches only the newest groupId, and unknown action types are dropped.
Clamp and sanity-check: amount between 1 and 1,000,000, at most 8 actions per
command, customer names under 60 characters, reminder time not in the past and
within 90 days.
Never put secrets, emails or phone numbers into a prompt. The system prompt stays
under about 600 tokens and is versioned ( PROMPT_VERSION  logged with each call).
Low confidence (below 0.6) or a missing required field turns into a clarify , never a
guess.

3.14 Auth and multi-tenancy rules
Goal: two shopkeepers can use the same deployment and never see, change or influence
each other's data.
3.14.1 Auth ﬂow
1. Register: validate with zod, hash the password with bcryptjs  (cost 10), create the
Shop, then the User with that shopId , sign a JWT { sub: userId, shopId } , and
set it as a cookie.
2. Login: look up by identifier ; always run a bcrypt compare (against a dummy hash if
the user doesn't exist) so response time doesn't reveal which identifiers exist; return
one generic error on any failure.
3. Cookie: httpOnly , sameSite: 'lax' , secure  in production, maxAge  7 days, name
bb_session . The JWT secret is at least 32 random characters from JWT_SECRET .
4. requireAuth middleware: verifies the cookie, sets req.auth = { userId, shopId } ,
otherwise returns 401 AUTH_REQUIRED . Add AUTH_REQUIRED  and AUTH_INVALID  to
the error codes in 3.13.3.
5. Logout: clears the cookie. /api/auth/me  returns { user, shop }  and is the single
source of truth on app load.
6. Rate limit login and register separately: 5 failures per 15 minutes per IP on login.
Cookie and domain rule: if web (Vercel) and API (Render) sit on different domains,
browsers treat the cookie as third-party and may block it. Avoid the problem by proxying:
add a Next.js rewrites()  entry that forwards /api/:path*  to the Express URL, so the
browser only ever talks to one origin. Locally it is the same origin story, so nothing
changes between dev and prod. If you must go cross-origin, use sameSite: 'none' ,
secure: true , CORS credentials: true  and fetch(..., { credentials: 'include'
}) .

3.15 Command history and deletion semantics
The Commands screen lets a shopkeeper review everything they said and delete any
command. Deleting a command means undoing everything it did, not just hiding a row.
One service function implements this, and both the screen's delete button and the voice
phrase "last wala hata do" call it.
3.15.1 What is stored
Every voice or typed command writes one ActionLog (see 3.4), including read-only ones
such as balance queries. Writes created by that command all carry the same groupId .
The list endpoint returns, per command, an effects  summary ( { entries, reminders,
stock, newCustomers }  counts) so the confirm dialog can say exactly what will go away
without a second request.
3.15.2 Delete algorithm ( DELETE /api/commands/:groupId )
1. Find the ActionLog with { shopId, groupId, deletedAt: null } . If none: 404 .
Deleting twice returns 200  with all counts zero, so the operation is idempotent.
2. Soft delete Entries with that groupId  (set deletedAt ), then recompute balances for
every affected customer from the remaining entries.
3. Reminders: pending  ones become cancelled . sent  ones stay sent  (an email can't
be recalled) and are reported in the response so the UI and voice reply can say so.
4. Stock items created by that command are removed; items whose status the command
changed are restored to the previous status.
5. Customers created by the command that now have no remaining entries are archived
( archivedAt ), not hard deleted.
6. Set deletedAt  on the ActionLog and emit ledger.updated  on the shop's SSE
stream.
7. Return { entriesRemoved, remindersCancelled, remindersAlreadySent,
stockReverted, customersArchived } .
3.15.3 Rules
Independent of order: entries are independent, append-only amounts, so deleting an
older command is safe; balances are recomputed, never adjusted by subtraction.
No hard deletes: rows stay in the database for audit and debugging. The default list
hides deleted commands.
Read-only commands (queries, summaries) have no effects; deleting one just hides it.

4.7 Design principles in depth
4.7.1 Principles with concrete rules
1. Voice first, screen second. The user should be able to finish a task without looking. So
every outcome is spoken, and the screen only confirms. Never require a tap after
speaking, except to retry an error.
2. Show system status at all times. Five states are always visible and visually distinct:
Idle, Listening, Thinking, Done, Needs-answer. If more than 400 ms passes with no
visible change, something is wrong with the design.
3. Trust through transparency. Show the heard transcript, then the understood actions.
If the transcript is wrong, the user sees why the result is wrong and can retry. Never
hide what the app did.
4. Forgiveness over confirmation. Don't ask "Are you sure?" for normal entries; make
undo one phrase or one tap instead. Ask only when the app truly cannot decide
(ambiguity or missing amount).
5. Numbers are the heroes. Money values are the largest, boldest text in any card. Use
tabular figures, Indian digit grouping and a rupee sign everywhere.
6. Plain and respectful language. Short words, "aap" form, no jargon like "entry" or
"transaction" in Hindi mode (use "hisaab", "likh diya", "jama").
7. One primary action per screen. The mic is always the biggest, brightest control.
Secondary controls are small, outlined and grey.
8. Consistent color meaning. Red always means money owed to the shop, green means
money received, amber means attention (stock, pending), blue means a system action
(reminder, email). Never reuse these colors decoratively.
9. Honest demo mode. Anything simulated is labeled with a small "Demo" chip, for
example the WhatsApp preview.

{
  const d       = useTransform(p, (v) => ((((i - v + N / 2) % N) + N) % N) -

  const x       = useTransform(d, (v) => Math.sin((v * 2 * Math.PI) / N) *
